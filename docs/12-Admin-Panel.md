# 12. Административная панель (Admin Panel)

Админ‑панель — отдельный раздел (`/admin/*`) для ролей `admin` и `super_admin` (канонический enum: `user`, `premium`, `admin`, `super_admin`; см. [`VALIDATION.md`](./VALIDATION.md#разрешение-противоречий)). Операционный `support` трактуется как alias/набор разрешений внутри admin без write-доступа к секретам, а не как отдельное значение enum. Использует те же REST‑эндпоинты `/api/v1/admin/*`. Ниже — функциональные блоки и их источники данных.

## A.1 Управление пользователями

- Список пользователей с фильтрами (статус, дата регистрации, план, активность).
- Просмотр карточки: профили поиска, подписки Telegram, согласия GDPR, журнал аудита.
- Действия: блокировка/разблокировка, сброс пароля (инициировать письмо), смена роли, принудительный logout (отзыв refresh‑токенов), **экспорт и удаление данных по GDPR**.
- Источник: `users`, `audit_logs`, `user_consents`.

## A.2 Управление источниками данных (Sources)

- CRUD источников: добавление/редактирование/выключение коннектора.
- Поля: тип (`api`/`scraper`), статус (`active`/`paused`/`degraded`), расписание (cron), приоритет, конфигурация (rate limit, селекторы, креды через ссылку на секрет‑менеджер).
- Кнопки: «Запустить сейчас», «Пауза», «Тестовый прогон» (dry‑run без записи в БД), «Просмотр последнего сырья (raw payload)».
- Источник: `sources`, `source_runs`.

## A.3 Мониторинг парсеров и API‑коннекторов

Единая таблица здоровья по каждому коннектору:

| Метрика | Описание |
|---------|----------|
| Last run / Next run | Время последнего и следующего запуска |
| Success rate (24h) | Доля успешных прогонов |
| Items fetched / new / duplicates | Объёмы за прогон |
| Avg latency | Среднее время прогона |
| Error rate, last error | 4xx/5xx, бан, CAPTCHA, schema drift |
| Status badge | 🟢 active · 🟡 degraded · 🔴 failing |

- Графики (встраиваются из Grafana через iframe/Grafana‑panel) по каждому источнику.
- Алерты `schema_drift`, `block_detected`, `success_rate_low` подсвечиваются.
- Источник: `source_runs` + Prometheus метрики.

## A.4 Просмотр логов

- Поиск по `correlation_id`, `source_id`, `user_id`, уровню, временно́му диапазону.
- Прямой переход в Loki/Grafana с предзаполненным запросом.
- Технические логи **не** хранятся в основной БД (только в Loki); в `audit_logs` — бизнес‑события.

## A.5 Управление очередями задач

- Просмотр состояния очередей (`collect`, `match`, `notify`, `dlq`): глубина, скорость обработки, число воркеров.
- Действия: повтор задачи из **Dead Letter Queue**, очистка, приостановка обработки очереди.
- Интеграция с BullMQ Dashboard (встроенный UI) для глубокой отладки.

## A.6 Управление уведомлениями

- Глобальный rate limit отправки, шаблоны сообщений (редактирование текста уведомления), тестовая отправка себе.
- Просмотр доставленных/недоставленных уведомлений, причин ошибок (бот заблокирован пользователем и т.п.).
- Источник: `notifications`.

## A.7 Статистика системы (Dashboard)

KPI‑плитки и графики:
- Активные пользователи (DAU/MAU), новые регистрации.
- Кол‑во активных поисковых профилей.
- Объявлений собрано / уникальных / за сутки по источникам.
- Совпадений (matches) и отправленных уведомлений.
- Среднее время «объявление появилось → уведомление доставлено» (ключевой бизнес‑SLA).
- Здоровье инфраструктуры (сводка из §15).

## A.8 Технические заметки

- Все админ‑действия пишутся в `audit_logs` (кто, что, когда, до/после).
- Чувствительные действия (удаление пользователя, смена роли) требуют повторного подтверждения и логируются с особой пометкой.
- UI: React + shadcn/ui, таблицы — TanStack Table, графики — Recharts + встроенные панели Grafana.
