# 4. Non-Functional Requirements (NFR)

## 4.1 Масштабируемость (Scalability)

| ID | Требование | Целевое значение |
|----|-----------|------------------|
| NFR-SCALE-1 | Горизонтальное масштабирование stateless‑компонентов (API, воркеры). | Добавление инстансов без изменения кода. |
| NFR-SCALE-2 | Воркеры сбора масштабируются независимо от API. | Отдельный пул на источник/тип задач. |
| NFR-SCALE-3 | Поддержка количества источников. | 20+ без рефакторинга ядра. |
| NFR-SCALE-4 | Поддержка объёма объявлений. | 5–10 млн активных записей. |
| NFR-SCALE-5 | Поддержка пользователей. | 100 000 пользователей, 300 000 профилей. |
| NFR-SCALE-6 | Пропускная способность матчинга. | 1000 новых объявлений/мин против 300k профилей. |

**Стратегия:** очереди задач (BullMQ/Redis) развязывают ingestion, matching и notification. Каждый этап — отдельный пул воркеров, который масштабируется по длине очереди (KEDA/HPA по метрике queue depth).

## 4.2 Отказоустойчивость (Reliability / Resilience)

| ID | Требование |
|----|-----------|
| NFR-REL-1 | Падение одного коннектора не влияет на остальные (изоляция плагинов). |
| NFR-REL-2 | Circuit breaker на источник: при пороге ошибок источник временно отключается. |
| NFR-REL-3 | Идемпотентность задач: повторная обработка не создаёт дублей и повторных уведомлений. |
| NFR-REL-4 | Очереди с retry + exponential backoff + Dead Letter Queue. |
| NFR-REL-5 | Graceful shutdown воркеров (дообработка текущей задачи). |
| NFR-REL-6 | Деградация: при недоступности части источников система продолжает работать. |
| NFR-REL-7 | RPO ≤ 15 мин, RTO ≤ 1 час (см. Backup). |

## 4.3 Производительность (Performance)

| ID | Метрика | Цель |
|----|--------|------|
| NFR-PERF-1 | p95 latency REST API (чтение) | < 200 мс |
| NFR-PERF-2 | p95 latency REST API (запись) | < 400 мс |
| NFR-PERF-3 | Задержка «новое объявление → Telegram» | SLO p95 < 60 c; hard-alert при > 5 мин |
| NFR-PERF-4 | Время матчинга одного объявления | < 500 мс |
| NFR-PERF-5 | Дедупликация одного объявления | < 100 мс |

**Стратегия:** индексы БД под фильтры, частичная инвертированная индексация профилей, кэш геокодирования, предвыборка кандидатов профилей по «грубым» признакам (город, ценовой диапазон) перед точным матчингом.

## 4.4 Безопасность (Security)

См. детально [Security & GDPR](./13-Security-GDPR.md). Ключевое:
- TLS 1.3 везде, HSTS.
- JWT (RS256) + refresh‑ротация, короткий TTL access‑токена.
- Argon2id для паролей.
- Rate limiting и брутфорс‑защита.
- Принцип наименьших привилегий, секреты в Vault/secret manager.
- OWASP Top 10 mitigations, регулярный dependency scanning.

| NFR-LOG-6 | Никаких персональных данных и секретов в логах (маскирование). |

## 4.7 Резервное копирование (Backup & DR)

| ID | Требование |
|----|-----------|
| NFR-BAK-1 | Ежедневный полный бэкап PostgreSQL + непрерывный WAL‑archiving (PITR). |
| NFR-BAK-2 | Бэкапы шифруются и хранятся в отдельном регионе/бакете (S3). |
| NFR-BAK-3 | Retention: 7 ежедневных, 4 еженедельных, 12 месячных. |
| NFR-BAK-4 | Регулярное тестовое восстановление (раз в квартал). |
| NFR-BAK-5 | RPO ≤ 15 мин (через WAL), RTO ≤ 1 час. |

## 4.8 GDPR и защита персональных данных

См. [Security & GDPR](./13-Security-GDPR.md). Ключевое:
- Минимизация данных, явное согласие, журнал согласий.
- Право на доступ, исправление, удаление, переносимость.
- Шифрование PII at-rest и in-transit.
- Data Processing Agreement с провайдерами.
- Псевдонимизация в аналитике.
