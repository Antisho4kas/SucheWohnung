# 18. Future Scaling Strategy

## 18.1 Масштабирование источников (до десятков)

- **Connector SDK + реестр плагинов** (см. §9) — добавление источника = новый пакет, без правок ядра.
- **Self‑service генератор коннектора** (`npx create-connector`): scaffold с шаблоном маппинга, тестами и манифестом.
- **Каталог коннекторов** с метриками здоровья — приоритезация поддержки по ценности источника.
- **Кросс‑соурс дедупликация**: единый `global_listing_id` для одной квартиры с нескольких порталов (геофингерпринт + цена + площадь + перцептивный хеш фото).
- **Адаптивный планировщик**: частота опроса источника зависит от его «продуктивности» (сколько новых матчей даёт) и стоимости.

## 18.2 Масштабирование нагрузки

| Узкое место | Стратегия |
|-------------|-----------|
| API throughput | Horizontal scaling stateless‑инстансов за LB; CDN для статики |
| Очереди/воркеры | KEDA‑автоскейл по `queue_depth`; отдельные пулы по типу задач |
| PostgreSQL чтение | Read‑replicas, кэш Redis, материализованные представления |
| PostgreSQL запись/объём | Партиционирование `listings`/`listing_history`/`audit_logs` по времени; архивирование «холодных» данных в S3/Parquet |
| Поиск/гео | Вынести матчинг в специализированный индекс (Elasticsearch/OpenSearch) при росте сложности фильтров |
| Глобальный рост | Шардирование по региону/Bundesland; UUIDv7 уже готов к шардингу |

## 18.3 Эволюция архитектуры (monolith → services)

1. **Сейчас:** модульный монолит API + отдельные воркеры (см. §5).
2. **Триггеры выделения сервиса:** независимый профиль нагрузки, отдельный цикл релизов, изоляция отказов.
3. **Кандидаты на выделение:** Ingestion (уже почти отдельный), Notification Service, Matching Service, Telegram Gateway.
4. **Контракты:** межсервисное общение через события (outbox → broker) и узкие REST/gRPC API. Schema registry для событий.

## 18.4 Продуктовое масштабирование (будущие возможности)

- Доп. каналы уведомлений: Email, Push (PWA), WhatsApp, Signal.
- ML‑ранжирование релевантности и предсказание «хороших сделок» (цена ниже рыночной).
- Гео‑скоринг: близость к работе/транспорту/инфраструктуре (изохроны).
- Сохранённые поиски с авто‑заявкой/шаблоном письма арендодателю.
- Платные тарифы (приоритетные уведомления, больше профилей) — модель монетизации.
- Мульти‑страновое расширение (Австрия, Швейцария) — каноническая модель уже абстрагирует страну.

## 18.5 Принцип, обеспечивающий масштабируемость

> **Ядро ничего не знает об источниках, каналах и фильтрах конкретно — оно знает только контракты.** Любое расширение (источник, фильтр, канал) добавляется как плагин/конфигурация, а не как правка ядра. Это инвариант, который защищается контрактными тестами в CI.
