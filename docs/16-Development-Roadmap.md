# 16. Development Roadmap

Roadmap отражает три этапа из ТЗ с разбивкой на спринты, артефакты и Definition of Done.

## Этап 1 — Базовая платформа (≈ 6–8 недель)

| Спринт | Содержание | Definition of Done |
|--------|-----------|--------------------|
| S1 | Каркас репозитория (monorepo), CI/CD скелет, Docker Compose, окружения, базовая схема БД + миграции | `docker compose up` поднимает стек; CI зелёный |
| S2 | Авторизация (регистрация, login, JWT, refresh, reset, верификация email), RBAC | Пользователь регистрируется и логинится; тесты на auth |
| S3 | CRUD поисковых профилей + фильтры (EAV‑модель), REST API + OpenAPI | Профиль с фильтрами создаётся/редактируется через API |
| S4 | Telegram‑бот: привязка аккаунта, /start, /stop, базовые команды; система уведомлений (очередь notify, шаблон сообщения) | Тестовое уведомление доходит в Telegram |
| S5 | Frontend: дашборд, формы профилей/фильтров, управление подписками; админ‑панель v1 (пользователи, источники, логи) | Пользователь управляет всем из UI |
| S6 | Observability (Prometheus/Grafana/Loki/Sentry), хардненинг, нагрузочное тестирование каркаса | Дашборды и алерты работают |

**Выход Этапа 1:** работающая платформа без реальных источников (можно прогнать через mock‑коннектор).

## Этап 2 — Первый источник: Immobilienscout24 (≈ 4–6 недель)

| Спринт | Содержание | Definition of Done |
|--------|-----------|--------------------|
| S7 | Реализация коннектора IS24 (API при наличии партнёрского доступа, иначе scraping через Playwright), нормализация в каноническую модель | Объявления попадают в БД нормализованными |
| S8 | Дедупликация (fingerprint + near‑dup), проверка качества данных (валидация, скоринг), планировщик инкрементальных обновлений | Дубликаты отсекаются; «грязные» объявления отбраковываются |
| S9 | Матчинг профиль↔объявление end‑to‑end → реальные уведомления в Telegram; антибан (прокси, троттлинг) | Пользователь получает реальные релевантные квартиры |
| S10 | Мониторинг источника (success rate, дрейф), стабилизация, отказоустойчивость скрейпера | Алерты на падение источника; неделя стабильной работы |

**Выход Этапа 2:** полный сквозной поток от сбора до уведомления на одном реальном источнике.

## Этап 3 — Масштабирование (continuous)

| Веха | Содержание | Definition of Done |
|------|-----------|--------------------|
| M1 | Финализация Connector SDK + реестр плагинов + контрактные тесты | Новый коннектор добавляется без правок ядра |
| M2 | Подключение источника №2 (напр. Kleinanzeigen) по SDK | Источник работает за < 1 спринта силами одного разработчика |
| M3 | Унификация дедупликации между источниками (кросс‑соурс) | Одна квартира с 2 порталов = 1 уведомление |
| M4 | Шаблон/генератор нового коннектора, документация для разработчиков интеграций | Онбординг нового источника по чеклисту |
| M5+ | Подключение источников 3…N, переезд тяжёлых модулей в отдельные сервисы при росте нагрузки | Десятки источников без деградации |

## Зависимости и критический путь
- БД‑схема и Connector Contract — фундамент, блокируют почти всё → делаются первыми.
- Telegram‑привязка нужна до сквозного теста уведомлений.
- Антибан/прокси — до промышленного скрейпинга (Этап 2, S9).
